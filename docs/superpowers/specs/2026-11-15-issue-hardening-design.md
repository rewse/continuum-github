# Issue 本文とモデル応答の扱いの見直し

## 目的

次のリリースに向けて、issue 本文とモデル応答の扱いで見つかった小さな問題をまとめて直す。対象は次の 4 つで、互いに独立している。

1. モデル応答の stop reason
2. フォールバック注記の文言
3. issue 本文の Markdown 無害化
4. リリースノートの破壊的変更表示

pentest の Attack script をセクション用プロンプトから外す修正と、`content_filtered` を独立した理由でログに出す修正は `c6669a3` で main に入っている。本仕様はその続きで、同じリリースに入る。バージョン番号の更新とリリースは、全部の修正が入ったあとに別途行う。

## 1. stop reason

### 現状

`Bedrock.ask` が答えを捨てるのは、stop reason が `max_tokens` か `content_filtered` のときだけである。Converse API はほかに `guardrail_intervened`、`malformed_model_output`、`model_context_window_exceeded`、`tool_use` なども返す。これらのときの答えは不完全か想定外の形だが、マーカーがそろっていればそのまま使われる。

### 変更

答えを受け入れる stop reason を `end_turn` と `stop_sequence` に限る。それ以外はすべて捨てて、`model_failed purpose=<purpose> reason=<stop reason>` をログに出す。

ログに出す値は AWS が返す列挙値で、finding の内容を含まない。想定外の値がそのまま出るのを避けるため、`[a-z_]{1,40}` に完全一致しない値と、stop reason がない場合は `reason=unknown_stop` にする。

`_REJECTED_STOPS` は、受け入れる側の集合 `_ACCEPTED_STOPS` に置き換える。

## 2. フォールバック注記

### 現状

モデルがセクションを書けなかった issue の末尾には次の注記が付く。

> _Bedrock could not write the Summary, Why it matters, and Risk if left unresolved sections, so this issue shows the scanner's details only. A later sync tries again._

再試行は毎回の sync で行われるが、フィルターに当たる finding のように毎回失敗するものもある。「A later sync tries again」だと、いずれ埋まるように読める。

### 変更

注記の最後の文を「Each later sync tries again, and this note stays until one succeeds.」に置き換える。README の注記の例と、`sync` の説明にある「a later run tries again」も同じ意味に揃える。

既存の issue には旧文言の注記が残っている。`fill_sections` は本文に `FALLBACK_NOTE` がないときだけ本文を書き直すので、旧注記の issue は次に失敗したとき 1 回だけ新しい注記に書き直される。セクションが埋まれば本文全体が作り直され、注記は消える。移行処理は追加しない。

## 3. Markdown の無害化

### 現状

`render._escape` は `<` を `&lt;` にするだけで、スキャナーとモデルが書いた本文中の Markdown はそのまま描画される。害があるのは次の 2 つで、どちらも GitHub の Markdown API で確かめた。

- `@name` は user mention になり、そのユーザーに通知が飛ぶ。
- `![alt](url)` と参照形式の `![alt][ref]` は画像として埋め込まれ、GitHub の camo プロキシ経由で外部 URL を読み込む。

太字、見出し、リンク、コードブロックは pentest の詳細を読みやすくしているので残す。issue 参照（`#1`、`owner/repo#1`）は対象外にする。通知は飛ばないし、private リポジトリからの参照は権限のない人には見えないからである。

### 方式の比較

| 方式 | 利点 | 欠点 |
|---|---|---|
| A. コード以外の部分だけで mention と画像を置き換える | 見出し、太字、リンク、コードブロックがそのまま読める | フェンスとコードスパンを見分ける処理が要る |
| B. 詳細を丸ごとコードブロックに入れる | 実装が最も簡単 | pentest の詳細の見出しや太字がすべて生のテキストになる |
| C. 全体の `@` と `![` を置き換える | 簡単 | コードの中で `&#8203;` が文字のまま見え、攻撃スクリプトをコピーすると壊れる |

利用者が A を選んだ。

### 変更

本文に入るテキストを、コードとそれ以外に分けて扱う。

コードは次の 2 種類で、ここでは何もしない。GitHub はコードの中で mention と画像を処理しない。

- フェンスで囲まれたブロック: 行頭の 0〜3 個の空白に続く 3 個以上の `` ` `` か `~` で始まる。`` ` `` のフェンスで、情報文字列（フェンスの後ろの残り）に `` ` `` を含む行はフェンスにならない。閉じフェンスは、行頭の 0〜3 個の空白に続く、開きと同じ文字で同じ数以上の列と、後ろの空白だけの行である。閉じフェンスがないブロックは、CommonMark と同じくテキストの最後までをコードとみなす。
- インラインのコードスパン: フェンスの外で、同じ長さのバッククォート列で囲まれた範囲。範囲が空行（空白だけの行）をまたぐものはコードスパンにしない。対になる列がないバッククォートは普通の文字として扱う。

判定は CommonMark より狭くなる向きにだけずらす。GitHub がコードとして描画するのに無害化側がコードとみなさない場合は、コードの中に `&#8203;` や `\` が見えるだけで済む。逆向きにずれると mention や画像が効いてしまうからである。インデントによるコードブロック（4 個以上の空白）はコードとみなさない。これも同じ理由による。

コード以外の部分では、次の 2 つを置き換える。

- mention: 後ろに英数字が続き、直前が英数字・`` ` ``・`/`・`@` のどれでもない `@`（テキストや行の先頭を含む）を `@&#8203;` にする。`&#8203;` はゼロ幅スペースの文字参照で、表示は `@name` のまま mention にならない。`a@example.com` のようなメールアドレスは直前が英数字なので変わらない。
- 画像: `![` を `!\[` にする。リンクとしても描画されず、文字のまま表示される。

`<` の `&lt;` 化は、これまでどおりコードの中も含めたテキスト全体に適用する。状態マーカーの正規表現は本文の先頭から探すので、コードの中に偽のマーカーが残ると読み違えるおそれがある。コードブロックの中で `&lt;` が文字のまま表示される既存の見た目の問題は、本仕様では扱わない。

無害化は `render.escape_text(text: str, *, inline: bool = False) -> str` にまとめる。`inline=True` は表のセルや 1 行の項目に使い、フェンスを判定しない。パッケージ内の他のモジュールから使うので先頭に `_` を付けないが、README には載せない。適用先は次のとおりである。

- `render`: `_escape` を通る箇所すべて（表のセル、モデルが書いたセクション、詳細の見出しと本文）。`_escape` は `escape_text` に置き換える。
- `report`: 週次レポート issue の本文。issue タイトルの行（`_line`）、モデルが書いた severity 要約、リポジトリ名とスキャン名の行が入る。タイトルは本文に入ると mention が効くので、ここでは対象になる。report の `_escape` を削除して `escape_text` を使う。

`_cell` は空白をまとめてから無害化するので、コードの判定もセルの中で行う。セルの中ではフェンスは成立しないので、効くのはコードスパンだけになる。

既存の issue 本文は作り直さない（設計者の判断）。sync は既存の本文の状態マーカーと Severity 行だけを差し替えるので、無害化は新しく作る本文と、セクションが埋まって作り直される本文にだけ効く。既存の issue の mention は作成時に通知が済んでおり、画像は利用者が開いたときだけ読み込まれる。一度だけ全部を作り直す処理は、書き込み回数に見合わない。

## 4. リリースノートの破壊的変更

### 現状

`cliff.toml` は各コミットの件名だけを出す。`refactor!:` や `BREAKING CHANGE:` フッターを持つコミットも、ほかと見分けがつかない。v0.4.0 のリリースノートでもパッケージ名の変更が目立たなかった。

### 変更

本文テンプレートの先頭に、破壊的変更のコミットがあるときだけ `### ⚠️ Breaking Changes` 節を置く。各項目には git-cliff の `commit.breaking_description` を 1 行で出す。この値は `BREAKING CHANGE:` フッターの本文で、フッターがなければ件名の説明部分になる。同じコミットは、種類別の節にもこれまでどおり出る。

## テスト

- stop reason: `end_turn` と `stop_sequence` は受け入れる。`guardrail_intervened` は捨てて `reason=guardrail_intervened` を出す。stop reason がない場合と `Bad Value!` は `reason=unknown_stop` を出す。
- 注記: `FALLBACK_NOTE` が新しい文で終わる。
- 無害化: 段落中の `@name`、`![a](u)`、`![a][r]` は置き換わる。フェンスとコードスパンの中、メールアドレス、閉じていないフェンスより後は変わらない。空行をまたぐバッククォートの対と、情報文字列に `` ` `` を含む行の後ろは置き換わる。`<` はコードの中でも `&lt;` になる。issue 本文全体（詳細とセクション）と週次レポートの本文（タイトルの行と要約）にも適用されることを確かめる。
- リリースノート: `git cliff v0.3.0..v0.4.0 --tag v0.4.0` の出力で、`refactor!:` のコミットが破壊的変更の節に出ることを目で確かめる。

## 対象外

- issue タイトルそのもの。GitHub はタイトルで mention を処理しない。
- 既存の issue 本文の作り直し。
- 週次のビジュアルレポート（HTML）。workflow artifact で、GitHub の Markdown を通らない。
- 利用側リポジトリの WAF sync。同じ無害化を、利用側の別の仕様で入れる。
- バージョン番号の更新とリリース。
